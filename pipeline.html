How a guide becomes a finding you can trust

npx modern-web-guidance analyze finds old web platform code in an existing app and points each finding at the guide that replaces it. If it cries wolf, people stop listening.. so most of this pipeline is about one question: is this finding real?

Agents wrote all of it (rules, tests, scripts, even this page). Paul sets the bar, the corpus split, and the guardrails, and makes the calls the judges can't.

Sometimes there's nothing to find

We used to ask agents to find the legacy pattern for every guide.. and they always found one. :) Now no-legacy-pattern is a valid answer. 62 of the 205 triaged guides got it, and they don't get a rule.

Does the fix change anything?

If adopting the guide doesn't change anything for the developer or the user, we don't report it. That's why the rule rewriting working +/~ selectors as :has() got retired. Same behavior, new syntax (and :has() can be slower).

Overlaps go to the more specific guide

When two guides could flag the same code, the more specific one owns it. The general rule excludes that case in its own matcher, so there's no dedup step later.

Every claim quotes the guide

Triage claims have to quote guide.md verbatim or they're dropped. Rules also store a hash of their guide, so editing a guide flags its rules for a re-check.

Corpus split · Build · Measure agents builddeterministic split
How do we know a rule works on code it's never seen?

Agents write and tighten rules on one half of the corpus. The rule gets graded on the other half, which no rule author ever opens. A hash of each repo's name decides the halves (and doubles as the wall between those two jobs).

Build · rule-writing

  • Authors (Gemini Pro) read the guide and its triage entry, then write a Static Matcher (~50–150 lines, with required fastTokens) against rule-writing code.
  • Matchers never call an LLM. They skip vendored, generated, and >1 MB files.
  • diagnose-rule-writing.ts runs the judge panel and the verifier over up to 25 rule-writing findings (≤ 2 per repo, no docs or tests) and writes up a dossier of the false positives and verifier drops.
  • Real false positives from the dossier become negative unit tests. Repeat until rule-writing precision clears the bar.
  • Every validated finding still has to fire (losing one needs a written reason in accepted-regressions.json), and the D-084 recall and selectivity tests have to pass.
  • Every commit gets a fresh-context review of its git show (independent reviewer agent). Once a rule clears the rule-writing bar, it gets scored on held-out from committed code (at-commit.ts).

Measure · held-out

  • Authors see the numbers, never the cards. An edited rule gets re-scored on the same held-out split (we don't go mine fresh shards for it).
  • Cards come from unseen repos (≤ 2 per repo, no docs or test paths).
  • The judge panel and the verifier read the same cards (more on that in 3). Disagreements and scope calls go to Paul.
  • There's one sanctioned hole in the wall: validated-regressions.ts names validated findings by file and line.

Where do we need an LLM, and why are there two?

Hashing, sampling, matching and the thresholds are all deterministic code. Code is bad at context though.. is this scrollHeight math an auto-growing textarea or an animation? Is that hidden checkbox part of a toggle switch? Two LLM roles make those calls, and neither sees the other's notes.

LLM Verifier

“Should this finding be reported, here?”

It reads the finding's code, guide.md, and the rule's own Keep when / Drop when, then says keep or drop.

In a real app, the verifier is the developer's own coding agent, applying the rubric from analyze --json (no extra API key or cost).

For measurement we run it over the same blind cards, which is where Post-Verifier Precision comes from. Paul spot-checks its drops with sealed decks too.

Why keep the judge blind?

Same 45 findings, three different inputs. Here's how often the judge said legit:

When does a rule run by default?

The judge panel scores each rule on its own held-out findings. Two numbers decide it: how often the raw matcher is right, and how often it's right after the verifier's pass. Until both clear the bar, the rule stays off by default (you can still run it with --all).

Qualified default-on

Post-Verifier Precision ≥ 90% and either Static Matcher Precision ≥ 80% at n ≥ 10, or ≥ 90% at n ≥ 5 for rare patterns. Runs in every npx modern-web-guidance analyze (and a guide is on by default if any of its rules qualifies).

Scope Hold held-pending-paul

Clears the bar, but the scope or payoff needs a human call. Paul promotes it or declines it.

Experimental --all only

Below the bar, or not enough held-out findings to judge yet. Back to Build: tighten on rule-writing, then re-score on the same held-out split.

Retired

Needs a written reason, a decision ID, and Paul's OK.

Where should the dial sit? Tolerating 1 false alarm in 10 vs 1 in 5 changes how many rules ship. Paul picked 80% static and 90% post-verifier (the coding agent's verify step covers the gap between the two).

Detect

analyze --json runs the qualified rules (no LLM, no API key). Each finding comes with its rule's Keep when / Drop when.

Verify, then plan

The agent plays the LLM Verifier: it applies Keep / Drop to every finding, then reports back before touching any code.

Update

retrieve <guide-id> pulls the guide, then the agent rewrites the code and runs the app's own tests. Why no --fix? Even the “simple” swaps had behavior traps.

Who builds it
If agents write all of it, why trust it?

Nobody hand-writes rules here. The trust comes from the process around the agents: who's allowed to see what, who checks whose work, and which calls stay human.

Paul
human · meta-meta review

Sets the bar, the corpus split, and the guardrails.

Grades judge disagreements and scope/payoff calls, spot-checks the judge and the verifier with sealed decks, and signs off on any rule retirement.

Doesn't read rule files line by line (that's what the process is for).

Conductor
agent

Plans each wave, briefs agents, reviews, merges, keeps PLAN.md. Doesn't edit code itself.

Authors
Gemini Pro

Triage guides, write and tighten rules, dig into failures. One worktree each.

Reviewers
fresh context · Pro High · reviewer

Read every commit's git show and red-team rules, triage, and the scorecard. One fix pass.

Judge panel
3-pass Flash + Pro

Grades blind held-out cards. Never sees rule-writer text.

Process observer
different model family

Audits the process itself at the end of each wave and before any promotion.

Mechanical work
Flash

Materializing corpus data, doc sync, diff checks.
